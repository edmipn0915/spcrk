## 一、架构审计总览

### 1.1 审计方法

| 审计范围 | 覆盖内容 |
|----------|----------|
| 全量源码 | `app/src/main/java/com/spcrk/app/` 全部 103 个文件 |
| 依赖审计 | `app/build.gradle` 全部 30 项直接依赖 + 传递依赖 |
| 分层耦合 | 27 个 Composable 屏幕、10 个 ViewModel、全部 Manager/Repository/Store |
| 对外边界 | 全部出站 HTTP 调用、MCP 连接、本地子进程 |

### 1.2 对外前后端分离结论：✅ 完全分离（纯客户端）

项目 **零内嵌服务端**，所有网络成分为出站客户端请求：

| 检查项 | 结果 | 证据 |
|--------|------|------|
| HTTP 服务器 / Socket 监听 | ❌ 无 | 无 ServerSocket/NanoHTTPD 等监听代码 |
| Node / koa / express | ❌ 无 | 无 package.json/node_modules（MCP stdio 的 npx 子进程属外部命令，非内嵌服务） |
| Python 服务 | ❌ 无 | spcrk 下无 `.py`/`server/`（桌面旁 Mahjong 项目是另一独立应用） |
| 端口监听 | ❌ 无 | Manifest 仅 INTERNET 出站权限 |
| 外部服务调用 | ✅ 大量 | OpenAI 等 60 家 LLM 端点、搜索引擎、MCP 服务器、Ollama 等 |

**关键判断**：App 永远是 HTTP 客户端。`localhost:11434 / :1234 / :8000`（Ollama / LM Studio / GPUStack）指向设备上独立的本地推理进程，App 只是其 HTTP 客户端，属"外部进程依赖"，非内嵌服务。

### 1.3 对内 UI↔逻辑分层结论：⚠️ 部分分离（约半数屏幕规范）

- ✅ **11/27 屏幕** 走标准 MVVM：经 ViewModel 间接调用业务逻辑
- ❌ **15/27 屏幕** 直接在 Composable 内 `new` 业务对象（Manager/Repository/Store）
- ⚠️ **3 处架构异常**：VM→Activity 引用、VM→View Manager 泄漏、VM 与 View 同文件定义
- 无 DI 框架（Hilt/Koin），全部手工 `new` / Application 强转，不可测试替换

## 四、前后端分离方案（架构重构）

### 4.0 重构目标

把当前"UI ↔ Manager 紧耦合"的散乱依赖，**重塑成 6 层单向依赖链**，核心是 **Domain Interface + Domain Model**：

```
Compose
  ↓
ViewModel
  ↓
UseCase
  ↓
Domain Interface
  ↓
Implementation
  ↓
Room   File   Network/AI/MCP
```

**核心理念**：
- **Domain Interface + Domain Model 是整套架构的重心**——UseCase 只对接口编程，不感知 Room / OkHttp / AI Manager / SQLite Entity / API JSON 任何实现细节
- **UI 完全不知道 Room / OkHttp / AIManager / API JSON / MCP / SQLite Entity**——UI 见到的是 Domain Model 或 UiModel，与传输/存储格式解耦
- **替换底层实现时，只要 Domain Contract 保持兼容，UI / ViewModel / UseCase 无需修改**；若业务能力或 Domain Contract 本身发生变化（如从文本聊天升级为流式多模态、新增工具调用、新错误模型），则只修改受影响的上层业务接口
- **AppContainer 是组装器，不是 Service Locator**——它负责在 Application 层创建 Implementation → UseCase → ViewModel，**UI 不主动到 AppContainer 取依赖**，依赖通过构造注入流向 UI

### 4.1 六层职责边界

| 层 | 包路径（建议） | 职责 | 依赖 | 禁止 |
|----|---------------|------|------|------|
| **UI（Compose）** | `ui/` | 屏幕布局、动画、主题、导航；订阅 `StateFlow<UiState>` 渲染 | ViewModel | 直接访问 Room、OkHttp、AI Manager、API JSON、SQLite Entity、MCP |
| **ViewModel** | `ui/*ViewModel.kt` | 持有 `StateFlow<UiState>`；接收 UI 事件、调用 UseCase；**不持有任何 Repository/Manager 实例**，只持有 UseCase | UseCase | 直接访问 Room、OkHttp、Repository；通过 getter 暴露 Manager 给 View |
| **UseCase** | `domain/usecase/`（新增） | 单一业务操作（SendMessage / DownloadVideo / ListMcpTools 等）；组合 1~N 个 Repository；输入校验、业务规则；**纯 Kotlin** | Repository Interface + Domain Model | 持有 ViewModel 引用；import Compose |
| **Domain Interface** | `domain/repository/`、`domain/model/`（新增） | **架构核心**：定义 `XxxRepository` 接口 + `XxxModel` data class；接口的入参/出参全部是 Domain Model，不暴露 Entity、JSON、Cursor 等实现细节 | Kotlin Stdlib、kotlinx.coroutines（suspend / Flow） | 任何 Room / OkHttp / Android SDK / API DTO |
| **Implementation** | `data/repository/`（新增）、`ai/`、`downloader/` | 实现 `Domain Interface`；把 Room Entity ↔ Domain Model 互转、把 JSON ↔ Domain Model 互转、调用 OkHttp/AI Manager 拿到数据后映射回 Domain Model | Domain Interface、Room、OkHttp、AI Manager、JSON | 被 ViewModel/UseCase 直接调用（只能通过 Interface） |
| **Infrastructure** | `core/db/`（Room）、`core/network/`（OkHttp）、`ai/`（Manager）、`downloader/` | Room Database / OkHttp Client / AI Manager / Search Engine / MCP Manager / Video Downloader / OCR / Document 等"原子能力"；无业务组合 | Android SDK、第三方库 | 引用 Domain Model 之外的任何上层类型 |

### 4.2 Domain Model 与 UiModel 边界

| 类型 | 定义 | 示例 | 可见范围 |
|------|------|------|----------|
| **Domain Model** | 业务核心数据，跨层共享 | `MessageModel(val id: String, val content: String, val createdAt: Instant)` | UI、ViewModel、UseCase、Repository、Implementation |
| **UiModel** | UI 专属展示状态，含 UI 行为标记 | `ChatMessageUi(val isExpanded: Boolean, val isStreaming: Boolean, val formattedTime: String, val isError: Boolean)` | UI 层内部（Compose 内转换，不跨层） |

**规则**：
- Domain Model 是纯 Kotlin data class，无平台依赖
- UiModel 在 Compose 内由 Domain Model + 交互状态组合生成（如 `message.toUiModel(isExpanded, isStreaming)`），**不进入 ViewModel 以下各层**
- ViewModel 暴露 `StateFlow<UiState>`，UiState 内同时持有 Domain Model 列表和 UI 状态（如 `val messages: List<MessageModel>, val isStreaming: Boolean`）

### 4.3 逐步淘汰"巨型 Manager" → 明确 DataSource

**当前问题**：`AIManager`、`McpManager`、`SearchEngine` 等类承担了"组合多个数据源 + 业务逻辑"双重职责，长期会演变为新的 God Object。

**目标命名**：

| 当前 | 建议 | 职责 |
|------|------|------|
| `AIManager` | `OpenAiDataSource` | 仅做 OpenAI 兼容 API 出站 HTTP + JSON 解析 |
| `SearchEngine` | `SearchDataSource` | 各搜索引擎出站 HTTP + 结果解析 |
| `McpManager` | `McpDataSource` | MCP 三种连接（SSE / HTTP / stdio 子进程） |
| `SkillManager` | `SkillDataSource` | 技能（天气 / 新闻 / 网页摘要）出站调用 |
| `VideoDownloader` | `VideoDataSource` | 视频直链解析 + 分块下载 |
| `DocumentManager` | `DocumentDataSource` | 本地文档（PDF / Word / Text）读取 |
| `OcrManager` | `OcrDataSource` | ML Kit OCR 本地识别 |

**Repository 负责组合**（业务逻辑留在 Domain 层，不在 DataSource 内部）：
```
ChatRepositoryImpl
    ├── OpenAiDataSource
    ├── McpDataSource
    └── SkillDataSource
```

### 4.4 长任务架构（下载 / WorkManager）

下载类长任务（视频下载、大模型下载、批量文档导入）**不能由 ViewModel 直接管理**——配置变更或进程重建后会丢失。

**目标分层**：

```
DownloadUseCase（Domain 层，组合 DownloadRepository）
      ↓
DownloadRepository（Domain Interface）
      ↓
DownloadWorker（Infrastructure，WorkManager）
      ↓
VideoDataSource / ModelDataSource（原子下载能力）
```

**规则**：
- ViewModel 只调用 `DownloadUseCase.start(url): Flow<DownloadProgress>`，不直接持有 `VideoDownloader`
- `DownloadWorker` 由 WorkManager 调度，进程重建后自动恢复
- 下载进度通过 `DownloadRepository.getProgress(id): Flow<DomainModel>` 暴露给上层
- UI 取消下载 = `DownloadUseCase.cancel(id)`，不直接操作 Worker

**总计**：约 **13 个工作日**（含单测）；不含单测约 **11 天**。

### 4.6 增量交付策略

不重写全部，按业务域**一个一个迁移**，每完成一个域立即获得收益：

| 里程碑 | 迁移内容 | 收益 |
|--------|----------|------|
| M1 | SettingsRepository（轻量、模型已存在） | 演示完整链路，6 层架构雏形 |
| M2 | NoteRepository + NoteViewModel + NoteEditScreen | 第一个端到端落地的屏幕 |
| M3 | DownloadHistoryRepository + HistoryScreen | 数据类多但 Repository 简单 |
| M4 | KnowledgeRepository + KnowledgeScreen | 引入 DocumentManager 的双 Model 映射 |
| M5 | ChatRepository（最复杂：流式 SSE + MCP + Skill） | 核心价值流 |

每个 M 完成后 6 层依赖都更清晰，UI/ViewModel 对底层的耦合都减少，**渐进式收益**而非"一次性大爆炸"。
