## 一、架构审计总览

### 1.1 审计方法

| 审计范围 | 覆盖内容 |
|----------|----------|
| 全量源码 | `app/src/main/java/com/spcrk/app/` 全部 103 个文件 |
| 依赖审计 | `app/build.gradle` 全部 30 项直接依赖 + 传递依赖 |
| 分层耦合 | 27 个 Composable 屏幕、10 个 ViewModel、全部 Manager/Repository/Store |
| 对外边界 | 全部出站 HTTP 调用、MCP 连接、本地子进程 |

### 1.2 对外前后端分离结论：✅ 完全分离（纯客户端）

项目 **零内嵌服务端**，所有网络成分为出站客户端请求：

| 检查项 | 结果 | 证据 |
|--------|------|------|
| HTTP 服务器 / Socket 监听 | ❌ 无 | 无 ServerSocket/NanoHTTPD 等监听代码 |
| Node / koa / express | ❌ 无 | 无 package.json/node_modules（MCP stdio 的 npx 子进程属外部命令，非内嵌服务） |
| Python 服务 | ❌ 无 | spcrk 下无 `.py`/`server/`（桌面旁 Mahjong 项目是另一独立应用） |
| 端口监听 | ❌ 无 | Manifest 仅 INTERNET 出站权限 |
| 外部服务调用 | ✅ 大量 | OpenAI 等 60 家 LLM 端点、搜索引擎、MCP 服务器、Ollama 等 |

**关键判断**：App 永远是 HTTP 客户端。`localhost:11434 / :1234 / :8000`（Ollama / LM Studio / GPUStack）指向设备上独立的本地推理进程，App 只是其 HTTP 客户端，属"外部进程依赖"，非内嵌服务。

### 1.3 对内 UI↔逻辑分层结论：⚠️ 部分分离（约半数屏幕规范）

- ✅ **11/27 屏幕** 走标准 MVVM：经 ViewModel 间接调用业务逻辑
- ❌ **15/27 屏幕** 直接在 Composable 内 `new` 业务对象（Manager/Repository/Store）
- ⚠️ **3 处架构异常**：VM→Activity 引用、VM→View Manager 泄漏、VM 与 View 同文件定义
- 无 DI 框架（Hilt/Koin），全部手工 `new` / Application 强转，不可测试替换

## 三、耦合屏幕重构路线图（15 个）

按依赖类型分组，分 4 个阶段实施：

### 阶段 1：基础设施 — AppContainer

**目标**：消灭散落在 UI 里的 `new Manager(...)` / Application 强转。

**新建 `AppContainer`**（挂在 `VideoDownloaderApp` 上）：
```
AppContainer
├── repository（单例，替代 (app as VideoDownloaderApp).repository）
├── settingsStore（替代 SettingsStore.getInstance()）
├── modelConfigStore
├── aimanager / searchEngine / mcpManager / skillManager
├── documentManager / ocrManager / localModelManager
└── videoDownloader
```

**屏幕取用**：`(LocalContext.current.applicationContext as VideoDownloaderApp).container.xxx`

**验收**：全项目 grep 无 `remember { XxxManager(...) }` 直接构造。

> 选 AppContainer 而非 Hilt：项目无 DI、无大量单测，手工容器 30 分钟落地，Hilt 是重写。

### 阶段 2：Manager 类屏幕拆 VM（7 个，按优先级排序）

| 优先级 | 屏幕 | 新建 ViewModel | 迁移内容 |
|--------|------|----------------|----------|
| 🔴 高 | `LocalModelScreen` | `LocalModelViewModel` | 下载/导入/删除全部方法 + 下载进度 StateFlow |
| 🔴 高 | `KnowledgeScreen` | `KnowledgeViewModel` | Repository 读写 + DocumentManager |
| 🔴 高 | `McpManageScreen` | `McpManageViewModel` | McpManager 全部调用（含 parse 工具） |
| 🟡 中 | `McpSettingsScreen` | `McpSettingsViewModel` | McpManager + Repository |

## 四、前后端分离方案（内部层间分离）

### 4.1 目标分层架构

```
┌─────────────────────────────────────────┐
│              UI Layer（ui/）              │
│   Composable 屏幕 + 纯展示逻辑           │
│   禁止直接 import ai/data 包              │
├─────────────────────────────────────────┤
│           ViewModel Layer（ui/）           │
│   StateFlow<UiState> + 事件函数          │
│   持有 UseCase/Repository 接口           │
├─────────────────────────────────────────┤
│           UseCase Layer（新增）           │
│   单一业务操作（如 SendMessageUseCase）    │
│   组合多个 Repository/Manager 调用        │
├─────────────────────────────────────────┤
│         Repository Layer（data/）          │
│   数据抽象接口 + Room Dao 实现           │
├─────────────────────────────────────────┤
│          Manager Layer（ai/）             │
│   外部服务客户端（AI/MCP/搜索/OCR）      │
│   实现 Repository 接口，供上层调用        │
├─────────────────────────────────────────┤
│        Infrastructure Layer（新增）        │
│   AppContainer / Network / Database        │
└─────────────────────────────────────────┘
```

### 4.2 各层职责边界

| 层 | 包路径 | 职责 | 禁止 |
|----|--------|------|------|
| UI | `ui/` | 屏幕布局、动画、主题、导航 | import ai/data 业务类 |
| ViewModel | `ui/*ViewModel.kt` | UI 状态持有、事件转发、调用 UseCase | 持有 Manager 对象、直接操作 Repository |
| UseCase | `domain/usecase/`（新增） | 单一业务操作、业务规则、输入校验 | 持有 ViewModel 引用 |
| Repository | `data/` | 数据抽象、Room DAO、SettingsStore | 持有 View/ViewModel 引用 |
| Manager | `ai/` | 出站 HTTP 客户端、MCP 连接、本地子进程 | 持有 View/ViewModel 引用、跨 Manager 直接调用 |
| Infrastructure | `core/`（新增） | DI 容器、网络配置、数据库构建 | 持有 View/ViewModel 引用 |

### 4.3 关键约束规则

1. **单向依赖**：UI → ViewModel → UseCase → Repository → Manager → Infrastructure，**上层不能跳过中间层直接调用底层**
2. **接口隔离**：UseCase/Repository 必须定义接口，实现可替换（便于单测 mock）
3. **数据类共享**：data 包的数据类（如 `Note`、`ChatMessage`）可被所有层引用，**视为不可变模型，不构成耦合**
4. **ViewModel 无状态泄漏**：禁止通过 getter 暴露 Manager/Repository 对象给 UI；UI 只读 `StateFlow` 的不可变快照
5. **UseCase 无 Compose 引用**：UseCase 是纯 Kotlin 类，禁止 import `androidx.compose.*`

### 4.4 对外"前后端分离"维持现状

**不改变以下已分离的部分**：
- 所有出站 HTTP 调用（OpenAI 等 60 家、搜索、Jina/Firecrawl）
- MCP 客户端模式（SSE / streamable HTTP / stdio）
- ML Kit 本地 OCR（无网络）
- 本地文档处理（PDFBox / POI）

**仅做一件事**：把 Manager 层的 HTTP 客户端**接口化**（定义 `AiProviderRepository`、`SearchRepository`、`McpRepository` 接口），实现与调用分离，便于：
- 替换供应商（如自研后端）时零改动 UI/ViewModel
- 单元测试 mock
